## 📝 Соглашение по оформлению коммитов и веток 

Для упрощения отслеживания изменений, автоматической генерации changelog'а и поддержания чистой истории разработки, мы используем стандартизированный формат написания коммитов  и наименования веток . 
✅ Формат коммитов 

Все коммиты должны соответствовать стандарту Conventional Commits . Это помогает автоматически генерировать changelog и понимать тип внесённых изменений. т.к. переменная прописана в GitLab)

```<type>: <краткое описание изменения>```

Примеры:
```commandline
feat: добавлен экран регистрации пользователя
fix: исправлено падение приложения при пустом ответе API
docs: обновлен README с инструкцией по установке
refactor: переписан компонент кнопки без использования HOC
perf: оптимизирована загрузка изображений
test: добавлены unit-тесты для формы авторизации
chore: обновлен eslint до версии 8.0.0
```

Допустимые типы (type): 

    feat — новая функциональность
    fix — исправление бага
    docs — изменения в документации
    style — изменения стиля кода (форматирование, точки с запятой и т.д.)
    refactor — рефакторинг без изменения поведения
    perf — улучшение производительности
    test — добавление или изменение тестов
    build — изменения, влияющие на сборку проекта
    ci — изменения конфигурации CI/CD
    chore — прочие правки, не связанные с исходным кодом
    revert — откат предыдущего коммита
     
Названия веток должны быть информативными и начинаться с номера задачи из трекера.
```<TICKET_ID> | <описание ветки>```

Примеры:
```
Selenium-324_fix-empty-api-response
Selenium-319_add-registration-screen
Selenium-321_update-eslint-config
```

Соблюдение этих правил помогает команде эффективнее работать с историей изменений и упрощает автоматизацию. Спасибо за аккуратность! 🙌

## 📥 Правила оформления Per Request'ов (PR) 

Чтобы упростить процесс код-ревью и сделать PR более понятным для ревьюеров, просим всех участников проекта соблюдать следующие правила при создании запросов на слияние. 
✅ Обязательные элементы PR
1. Заголовок  

    Должен быть понятным и описывать суть изменений.
    Желательно начинать с номера задачи из трекера.
     

Пример:  

```SELENIUM-324 | Fix crash on empty API response```
 
 
2. Описание PR  

В описании нужно кратко указать: 

    Что было сделано?
    Почему были внесены эти изменения?
    Ссылки на связанную задачу
    Если есть баги или нюансы — отметить это
     

💡 Это помогает ревьюерам быстро понять контекст и не задавать лишних вопросов. 
     

3. Указание ревьюера  

    При создании PR необходимо назначить одного или нескольких ревьюеров .
    Ревьюером должен быть человек, знакомый с темой/областью кода, которую вы меняете.
    Если вы не уверены, кто подойдёт — спросите у техлида или менеджера задачи.
     

4. Ссылка на задачу из трекера  

    Укажите ссылку на соответствующую задачу в описании PR.
    Если система позволяет — привяжите PR к задаче напрямую.

 
🛠 Советы 

    Делайте PR небольшими , по 200–300 строк изменений (если возможно).
    Разбивайте большие задачи на несколько PR.
     

Соблюдение этих правил делает разработку более предсказуемой, а ревью — эффективным и быстрым. Благодарю за аккуратность! 🙌
